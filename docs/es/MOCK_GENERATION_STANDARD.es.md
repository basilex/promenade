# Estándar de Generación de Mocks

Este documento define el enfoque unificado para la generación de mocks en todos los módulos del proyecto Promenade.

## Filosofía

**Todos los mocks DEBEN ser generados usando mockery** para garantizar:

- Consistencia en todos los módulos
- Sincronización automática con cambios de interface
- Herramientas estandarizadas e integración CI/CD
- Reducción de la carga de mantenimiento manual

## Configuración

El proyecto usa un archivo de configuración centralizado `.mockery.yaml` a nivel raíz que define la generación de mocks para:

- Core repositories (`internal/domain/repository`)
- Todos los módulos de negocio (`internal/modules/*/domain/repository`)

## Instalación

```bash
make install
# o manualmente:
go install github.com/vektra/mockery/v2@latest
```

## Uso

### Generar Todos los Mocks

```bash
make mocks
```

Este comando:

1. Verifica si mockery está instalado
2. Usa la configuración `.mockery.yaml`
3. Genera mocks para TODOS los repositories en TODOS los módulos
4. Coloca los mocks en ubicaciones estandarizadas

### Generar Mocks Específicos de Módulo

```bash
make mocks-audit      # Solo módulo Audit
make mocks-posts      # Solo módulo Posts
make mocks-profiles   # Solo módulo Profiles
make mocks-analytics  # Solo módulo Analytics
```

### Verificar que los Mocks Estén Actualizados

```bash
make mocks-verify
```

Esto es útil en pipelines CI/CD para asegurar que los desarrolladores no olvidaron regenerar los mocks después de cambios en las interfaces.

## Estándar de Ubicación de Mocks

Cada módulo sigue esta estructura:

```
internal/modules/{module_name}/
├── domain/
│   └── repository/
│       ├── {interface_name}.go           # Definición de interface
│       └── mocks/
│           └── {interface_name}_mock.go  # Mock generado
```

Para core repositories:

```
internal/
├── domain/
│   └── repository/
│       └── {interface_name}.go           # Definición de interface
└── adapter/
    └── repository/
        └── mocks/
            └── {interface_name}_mock.go  # Mock generado
```

## Estructura de Archivo de Mock

Todos los mocks generados tienen esta estructura:

```go
// Code generated by mockery v2.53.5. DO NOT EDIT.

package mocks

import (
    // imports...
)

// Mock{InterfaceName} is an autogenerated mock type
type Mock{InterfaceName} struct {
    mock.Mock
}

// Interface method implementations...
```

**NUNCA** edite estos archivos manualmente. Cualquier cambio será sobrescrito en la próxima generación.

## Usando Mocks en Pruebas

### Patrón Estándar

```go
package usecase

import (
    "testing"
    "github.com/stretchr/testify/mock"
    "github.com/basilex/promenade/internal/modules/audit/domain/repository/mocks"
)

func TestSomeUseCase(t *testing.T) {
    // Crear mock
    mockRepo := new(mocks.MockAuditEventRepository)

    // Establecer expectativas
    mockRepo.On("GetByID", mock.Anything, "test-id").Return(expectedEvent, nil)

    // Crear use case con mock
    uc := NewAuditEventUseCase(mockRepo)

    // Probar
    result, err := uc.GetEvent(ctx, "test-id")

    // Aserciones
    require.NoError(t, err)
    assert.Equal(t, expectedEvent, result)
    mockRepo.AssertExpectations(t)
}
```

## Independencia de Módulos

Los mocks de cada módulo son **completamente independientes**:

- Los mocks usan SOLO tipos de su propio módulo
- Sin imports de `internal/domain` o `internal/usecase`
- Solo se permiten imports de `pkg/*`
- Esto garantiza que los módulos puedan habilitarse/deshabilitarse independientemente

## Integración CI/CD

Agregue a su pipeline CI:

```yaml
- name: Verify mocks are up-to-date
  run: make mocks-verify
```

Esto asegura que los desarrolladores regeneren los mocks cuando cambien las interfaces.

## Cuándo Regenerar Mocks

Regenere los mocks cuando:

1. Agregue un nuevo método a una interface de repository
2. Cambie firmas de método (parámetros o tipos de retorno)
3. Agregue una nueva interface de repository
4. Elimine una interface de repository

## Convenciones de Nomenclatura

- **Interface**: `AuditEventRepository`
- **Mock**: `MockAuditEventRepository`
- **Archivo**: `audit_event_repository_mock.go`
- **Package**: `mocks`

Todos los nombres se derivan automáticamente por mockery del nombre de la interface.

## Migración desde Mocks Manuales

Si tiene mocks manuales (sin encabezado "Code generated by mockery"):

1. Haga backup de sus pruebas si dependen de comportamiento personalizado de mock
2. Ejecute `make mocks` para regenerar
3. Actualice las pruebas para usar patrones estándar de mockery
4. Elimine implementaciones de mock manuales

## Solución de Problemas

### Error: "mockery not found"

```bash
make install
```

### Error: "use of unsupported options detected"

Esta advertencia puede ignorarse. Aparece al usar flags de línea de comandos que sobrescriben la configuración `.mockery.yaml`.

### Las pruebas fallan después de la regeneración

Verifique que las expectativas de sus pruebas coincidan con las firmas reales de la interface. Mockery es estricto con los tipos.

### Al mock le falta el método esperado

Verifique que la interface tenga el método y regenere:

```bash
make mocks-{module}
```

## Mejores Prácticas

1. **Nunca commitee mocks manuales** - Siempre use mocks generados por mockery
2. **Regenere después de cambios de interface** - No olvide ejecutar `make mocks`
3. **Use `mock.Anything` para contextos** - A menos que esté probando comportamiento específico de contexto
4. **Valide expectativas** - Siempre llame `mockRepo.AssertExpectations(t)` al final de las pruebas
5. **Mantenga los mocks simples** - Comportamiento complejo indica que la interface puede ser demasiado amplia

## Resumen

✅ **HACER**:

- Usar mockery para TODA la generación de mocks
- Ejecutar `make mocks` después de cambios de interface
- Usar patrones de mock estándar en pruebas
- Mantener módulos independientes

❌ **NO HACER**:

- No editar archivos de mock generados manualmente
- No crear implementaciones de mock manuales
- No importar paquetes core en mocks de módulos
- No commitear mocks desactualizados que no coincidan con las interfaces

---

**Cumplimiento**: Este estándar es obligatorio para todos los módulos. Todos los mocks manuales existentes deben migrarse a mocks generados por mockery.
