# Padrão de Geração de Mocks

Este documento define a abordagem unificada para geração de mocks em todos os módulos do projeto Promenade.

## Filosofia

**Todos os mocks DEVEM ser gerados usando mockery** para garantir:

- Consistência em todos os módulos
- Sincronização automática com mudanças de interface
- Ferramentas padronizadas e integração CI/CD
- Redução da carga de manutenção manual

## Configuração

O projeto usa um arquivo de configuração centralizado `.mockery.yaml` no nível raiz que define a geração de mock para:

- Core repositories (`internal/domain/repository`)
- Todos os módulos de negócio (`internal/modules/*/domain/repository`)

## Instalação

```bash
make install
# ou manualmente:
go install github.com/vektra/mockery/v2@latest
```

## Uso

### Gerar Todos os Mocks

```bash
make mocks
```

Este comando:

1. Verifica se o mockery está instalado
2. Usa a configuração `.mockery.yaml`
3. Gera mocks para TODOS os repositories em TODOS os módulos
4. Coloca os mocks em localizações padronizadas

### Gerar Mocks Específicos de Módulo

```bash
make mocks-audit      # Apenas módulo Audit
make mocks-posts      # Apenas módulo Posts
make mocks-profiles   # Apenas módulo Profiles
make mocks-analytics  # Apenas módulo Analytics
```

### Verificar se os Mocks Estão Atualizados

```bash
make mocks-verify
```

Isso é útil em pipelines CI/CD para garantir que os desenvolvedores não esqueceram de regenerar os mocks após mudanças de interface.

## Padrão de Localização de Mocks

Cada módulo segue esta estrutura:

```
internal/modules/{module_name}/
├── domain/
│   └── repository/
│       ├── {interface_name}.go           # Definição de interface
│       └── mocks/
│           └── {interface_name}_mock.go  # Mock gerado
```

Para core repositories:

```
internal/
├── domain/
│   └── repository/
│       └── {interface_name}.go           # Definição de interface
└── adapter/
    └── repository/
        └── mocks/
            └── {interface_name}_mock.go  # Mock gerado
```

## Estrutura de Arquivo de Mock

Todos os mocks gerados têm esta estrutura:

```go
// Code generated by mockery v2.53.5. DO NOT EDIT.

package mocks

import (
    // imports...
)

// Mock{InterfaceName} is an autogenerated mock type
type Mock{InterfaceName} struct {
    mock.Mock
}

// Interface method implementations...
```

**NUNCA** edite esses arquivos manualmente. Quaisquer alterações serão sobrescritas na próxima geração.

## Usando Mocks em Testes

### Padrão Padrão

```go
package usecase

import (
    "testing"
    "github.com/stretchr/testify/mock"
    "github.com/basilex/promenade/internal/modules/audit/domain/repository/mocks"
)

func TestSomeUseCase(t *testing.T) {
    // Criar mock
    mockRepo := new(mocks.MockAuditEventRepository)

    // Definir expectativas
    mockRepo.On("GetByID", mock.Anything, "test-id").Return(expectedEvent, nil)

    // Criar use case com mock
    uc := NewAuditEventUseCase(mockRepo)

    // Testar
    result, err := uc.GetEvent(ctx, "test-id")

    // Asserções
    require.NoError(t, err)
    assert.Equal(t, expectedEvent, result)
    mockRepo.AssertExpectations(t)
}
```

## Independência de Módulos

Os mocks de cada módulo são **completamente independentes**:

- Mocks usam APENAS tipos do seu próprio módulo
- Sem imports de `internal/domain` ou `internal/usecase`
- Apenas imports de `pkg/*` são permitidos
- Isso garante que os módulos possam ser habilitados/desabilitados independentemente

## Integração CI/CD

Adicione ao seu pipeline CI:

```yaml
- name: Verify mocks are up-to-date
  run: make mocks-verify
```

Isso garante que os desenvolvedores regenerem os mocks quando as interfaces mudarem.

## Quando Regenerar Mocks

Regenere os mocks sempre que você:

1. Adicionar um novo método a uma interface de repository
2. Alterar assinaturas de método (parâmetros ou tipos de retorno)
3. Adicionar uma nova interface de repository
4. Excluir uma interface de repository

## Convenções de Nomenclatura

- **Interface**: `AuditEventRepository`
- **Mock**: `MockAuditEventRepository`
- **Arquivo**: `audit_event_repository_mock.go`
- **Package**: `mocks`

Todos os nomes são derivados automaticamente pelo mockery a partir do nome da interface.

## Migração de Mocks Manuais

Se você tem mocks manuais (sem cabeçalho "Code generated by mockery"):

1. Faça backup dos seus testes se eles dependem de comportamento customizado de mock
2. Execute `make mocks` para regenerar
3. Atualize os testes para usar padrões mockery padrão
4. Remova implementações de mock manuais

## Solução de Problemas

### Erro: "mockery not found"

```bash
make install
```

### Erro: "use of unsupported options detected"

Este aviso pode ser ignorado. Aparece ao usar flags de linha de comando que sobrescrevem as configurações `.mockery.yaml`.

### Testes falham após regeneração

Verifique se as expectativas dos seus testes correspondem às assinaturas reais da interface. Mockery é rigoroso com tipos.

### Mock está faltando método esperado

Verifique se a interface tem o método e regenere:

```bash
make mocks-{module}
```

## Melhores Práticas

1. **Nunca commite mocks manuais** - Sempre use mocks gerados pelo mockery
2. **Regenere após mudanças de interface** - Não esqueça de executar `make mocks`
3. **Use `mock.Anything` para contextos** - A menos que esteja testando comportamento específico de contexto
4. **Valide expectativas** - Sempre chame `mockRepo.AssertExpectations(t)` no final dos testes
5. **Mantenha mocks simples** - Comportamento complexo indica que a interface pode ser muito ampla

## Resumo

✅ **FAÇA**:

- Use mockery para TODA geração de mock
- Execute `make mocks` após mudanças de interface
- Use padrões de mock padrão em testes
- Mantenha módulos independentes

❌ **NÃO FAÇA**:

- Não edite arquivos de mock gerados manualmente
- Não crie implementações de mock manuais
- Não importe pacotes core em mocks de módulos
- Não commite mocks desatualizados que não correspondem às interfaces

---

**Conformidade**: Este padrão é obrigatório para todos os módulos. Todos os mocks manuais existentes devem ser migrados para mocks gerados pelo mockery.
