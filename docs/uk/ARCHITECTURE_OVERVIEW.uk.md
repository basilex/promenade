# Огляд архітектури Promenade

[🇬🇧 English](../ARCHITECTURE_OVERVIEW.md) | 🇺🇦 **Українська** | [🇩🇪 Deutsch](../de/ARCHITECTURE_OVERVIEW.de.md) | [🇵🇹 Português](../pt/ARCHITECTURE_OVERVIEW.pt.md) | [🇪🇸 Español](../es/ARCHITECTURE_OVERVIEW.es.md)

Цей документ надає високорівневий огляд архітектури Promenade, організованої навколо **принципів Clean Architecture** та **системи модулів на основі плагінів**.

---

## Рівні архітектури

### 1. Рівень додатку

**Розташування:** `cmd/api/main.go`

**Відповідальності:**

- Ініціалізувати інфраструктуру (DB, EventBus, Config, Logger)
- Завантажити основну конфігурацію
- Ініціалізувати систему модулів (виявлення, реєстрація, життєвий цикл)
- Запустити HTTP сервер

---

### 2. Основна інфраструктура

**Розташування:** `internal/infrastructure/`

**Компоненти:**

| Компонент     | Призначення                            |
| ------------- | -------------------------------------- |
| Database      | Управління підключенням до PostgreSQL  |
| Event Bus     | Memory/Redis Pub/Sub адаптери          |
| Scheduler     | Планування завдань на основі cron      |
| Config        | Завантажувач YAML конфігурації         |
| Logger        | Структуроване логування з slog         |
| Email Service | Асинхронна відправка електронної пошти |

**Надає:** Спільні сервіси для всіх модулів (DB, EventBus, Config, JWT, Logger)

---

### 3. Основний домен

**Розташування:** `internal/domain/entity/`

**Безпека і аутентифікація** (завжди ввімкнено):

- User (тільки аутентифікація: email, пароль, ролі)
- Session (JWT токени)
- Role (RBAC ролі)
- Permission (формат resource:action)

**Довідкові дані** (стабільні, спільні):

- Country (195+ ISO коди, регіони)
- Currency (170+ ISO 4217 коди)
- Timezone (500+ IANA часові пояси)
- Language (180+ ISO 639 коди)

**Призначення:** Основні сутності, необхідні ВСІМ модулям. Без бізнес-логіки.

---

### 4. Основні випадки використання

**Розташування:** `internal/usecase/`

**Доступні випадки використання:**

| Випадок використання | Призначення                      |
| -------------------- | -------------------------------- |
| Auth UseCase         | Реєстрація, логін, вихід         |
| Role UseCase         | CRUD ролей, призначення ролей    |
| Permission UseCase   | CRUD дозволів, контроль доступу  |
| Country UseCase      | Список країн, отримання за кодом |
| Currency UseCase     | Список валют, отримання за кодом |
| Purge UseCase        | Оркестрація завдань очищення     |

**Примітка:** Основні випадки використання НЕ містять бізнес-логіку - тільки інфраструктуру та безпеку.

---

### 5. Основні API маршрути

**Розташування:** `internal/adapter/http/v1/`

**Ендпоінти:**

| Маршрут                | Призначення                   |
| ---------------------- | ----------------------------- |
| /api/v1/health         | Перевірки здоров'я            |
| /api/v1/auth/\*        | Логін, реєстрація, вихід      |
| /api/v1/countries/\*   | Довідкові дані                |
| /api/v1/currencies/\*  | Довідкові дані                |
| /api/v1/roles/\*       | Управління RBAC               |
| /api/v1/permissions/\* | Управління RBAC               |
| /api/v1/admin/\*       | Очищення, управління системою |

## Система модулів

### Реєстр і менеджер модулів

**Розташування:** `pkg/module/`

**Призначення:** Оркеструє життєвий цикл модулів

**Функції реєстру:**

- `Register(module)` - Авто-реєстрація через `init()`
- `GetEnabled(config)` - Фільтрація увімкнених модулів з конфігурації
- `InitializeAll()` - Ініціалізація в порядку залежностей
- `StartAll()` - Запуск фонових воркерів
- `StopAll()` - Грациозне завершення

**Надає модулям:**

- Спільне підключення до БД
- Спільний EventBus
- Спільний JWT менеджер
- Спільний завантажувач Config

---

### Модуль: Posts

**Розташування:** `internal/modules/posts/`

**Статус:** Увімкнено (безкоштовно)

**Сутності:** Post, Comment, Like

**Функції:**

- Створення, оновлення, видалення постів
- Нитки коментарів (налаштовувана максимальна глибина)
- Вподобання постів і коментарів
- М'яке видалення з налаштовуваним утриманням

**Конфігурація:**

- max_content_length: 10000
- comments.max_depth: 10
- purge.user_posts.retention_days: 90
- purge.post_comments.retention_days: 30

**Маршрути:** /api/v1/posts/_, /api/v1/comments/_, /api/v1/likes/\*

---

### Модуль: Profiles

**Розташування:** `internal/modules/profiles/`

**Статус:** Увімкнено (безкоштовно)

**Сутності:** Profile, Contact

**Функції:**

- Управління профілями користувачів
- Контактна інформація (email, телефон тощо)
- Верифікація контактів
- Призначення основного контакту

**Конфігурація:**

- profiles.max_per_user: 1
- contacts.max_per_user: 5
- contacts.verification_required: true

**Маршрути:** /api/v1/profiles/_, /api/v1/contacts/_

---

### Модуль: Warehouse

**Розташування:** `internal/modules/warehouse/`

**Статус:** Вимкнено (комерційний - потребує ліцензії)

**Функції** (за наявності ліцензії):

- Управління інвентаризацією
- Відстеження запасів
- Сканування штрих-кодів
- Розташування на складі

**Маршрути:** /api/v1/warehouse/\* (коли увімкнено)

## Міжмодульна комунікація

### Event Bus

**Розташування:** `pkg/bus/`

**Адаптери:**

| Адаптер | Випадок використання        | Функції                     |
| ------- | --------------------------- | --------------------------- |
| Memory  | Dev/Test/Одна інстанція     | Швидкий, без залежностей    |
| Redis   | Production/Багато інстанцій | Розподілений, персистентний |

**Потік подій:**

1. Модуль A публікує подію в EventBus
2. EventBus розсилає всім підписникам
3. Модулі B, C, D обробляють подію асинхронно

**Приклади:**

- user.registered → надіслати привітальний email (асинхронно)
- post.created → оновити статистику користувача (асинхронно)
- purge.completed → логувати в аудит (асинхронно)

## Архітектура конфігурації

### Основна конфігурація

```
config/
├── app.dev.yaml     - Основна інфраструктура (dev)
├── app.test.yaml    - Основна інфраструктура (test)
├── app.prod.yaml    - Основна інфраструктура (prod)
└── modules.yaml     - Які модулі завантажувати
```

### Конфігурація модулів

```
internal/modules/posts/config/
├── config.dev.yaml  - Налаштування модуля Posts (dev)
├── config.test.yaml - Налаштування модуля Posts (test)
└── config.prod.yaml - Налаштування модуля Posts (prod)

internal/modules/profiles/config/
├── config.dev.yaml  - Налаштування модуля Profiles (dev)
├── config.test.yaml - Налаштування модуля Profiles (test)
└── config.prod.yaml - Налаштування модуля Profiles (prod)
```

**Перевизначення середовища:** `.env.example` (опціонально)

## Життєвий цикл модуля

### 1. Авто-реєстрація (через init())

Модуль реєструє себе при імпорті пакету:

```go
package posts

func init() {
    module.DefaultRegistry.Register(New())
}
```

### 2. Виявлення та фільтрація

- Читання `config/modules.yaml`
- Фільтрація увімкнених модулів
- Розв'язання залежностей (топологічне сортування)

### 3. Ініціалізація (в порядку залежностей)

Для кожного модуля:

- Завантажити конфігурацію модуля з `config/config.*.yaml`
- Налаштувати репозиторії
- Налаштувати випадки використання
- Налаштувати обробники
- Зареєструвати обробники очищення
- Зареєструвати політики утримання
- Зареєструвати дозволи

### 4. Реєстрація маршрутів

Для кожного модуля:

- Змонтувати маршрути модуля до роутера
- Застосувати middleware (auth, RBAC тощо)

### 5. Підписка на події

Для кожного модуля:

- Підписатися на відповідні події
- Налаштувати асинхронні обробники подій

### 6. Запуск (фонові воркери)

Для кожного модуля:

- Запустити cron завдання
- Запустити фонові воркери

### 7. Виконання

- Модулі обробляють HTTP запити
- Публікують/підписуються на події
- Виконують заплановані завдання

### 8. Завершення (на SIGTERM/SIGINT)

Для кожного модуля (в зворотному порядку):

- Грациозно зупинити воркери
- Закрити з'єднання
- Очистити ресурси

## Ключові принципи дизайну

### 1. CORE = ІНФРАСТРУКТУРА + ДОВІДКОВІ ДАНІ

- Core надає сервіси (DB, EventBus, Config, JWT)
- Core містить стабільні довідкові дані (країни, валюти)
- Core управляє безпекою (auth, RBAC)
- Core НЕ містить бізнес-логіку

### 2. МОДУЛІ = БІЗНЕС-ЛОГІКА

- Модулі є самодостатніми вертикальними зрізами
- Модулі володіють своїми сутностями, випадками використання, адаптерами
- Модулі реєструють обробники, політики, дозволи
- Модулі можна вмикати/вимикати через конфігурацію
- Модулі НЕ імпортують з `internal/domain` або `internal/usecase`
- Модулі НЕ залежать один від одного безпосередньо (використовують події)

### 3. АРХІТЕКТУРА ПЛАГІНІВ

- Динамічне завантаження через реєстр модулів
- Розв'язання залежностей (топологічне сортування)
- Управління життєвим циклом (init → start → stop)
- Авто-реєстрація через `init()`

### 4. АВТОНОМІЯ КОНФІГУРАЦІЇ

- Core: `config/app.*.yaml` (тільки інфраструктура)
- Модулі: `internal/modules/{name}/config/config.*.yaml`
- Кожен модуль завантажує свою власну конфігурацію
- Конфігурації специфічні для середовища (dev, test, prod)

### 5. СЛАБКЕ ЗВ'ЯЗУВАННЯ

- Комунікація на основі подій (pub/sub)
- Патерн реєстру (обробники, політики, дозволи)
- Залежності на основі інтерфейсів
- Без прямих імпортів модуль-до-модуля

### 6. ПІДТРИМКА ЛІЦЕНЗУВАННЯ

- Ліцензійні ключі для кожного модуля
- Валідація ліцензії в `Initialize()`
- Грациозна деградація при невалідній ліцензії

## Переваги

### Модульність

- Додавати нові модулі без торкання core
- Видаляти модулі без порушення інших
- Тестувати модулі незалежно

### Масштабованість

- Комерційні модулі (warehouse, fleet, finance)
- Увімкнення функцій на основі ліцензій
- Легко додавати нові вертикалі

### Підтримуваність

- Чіткі межі (core vs модулі)
- Єдина відповідальність (кожен модуль володіє своїм доменом)
- Ясність конфігурації (не монолітна конфігурація)

### Тестованість

- Юніт-тестування модулів ізольовано
- Інтеграційне тестування з реальним/мок core
- Smoke-тести критичних потоків

### Розгортуваність

- Вмикати тільки потрібні модулі на розгортання
- A/B тестування нових модулів
- Поступовий розгорт функцій

## Поточний стан

### Core

- Інфраструктура (DB, EventBus, Scheduler, Config, Logger)
- Безпека (Auth, RBAC, JWT, Sessions)
- Довідкові дані (Countries, Currencies, Timezones, Languages)
- Управління модулями (Registry, Lifecycle, Config Loader)
- Оркестрація очищення (на основі реєстру, без знань про сутності)

### Модулі

- **Posts** (posts + comments + likes) - Повністю незалежний
- **Profiles** (profiles + contacts) - Повністю незалежний
- **Warehouse** (inventory management) - Комерційний, вимкнений

### Відповідність архітектури

- Core містить ТІЛЬКИ інфраструктуру + довідкові дані
- Модулі ПОВНІСТЮ незалежні (без імпортів core)
- Конфігурація АВТОНОМНА (кожен модуль володіє конфігурацією)
- Ліцензування ПІДТРИМУЄТЬСЯ (готовий для комерційних модулів)

### Нещодавні покращення

- Система очищення відрефакторена (core = оркестратор, модулі = воркери)
- Profiles/Contacts мігровано в модуль (видалено з core)
- 15,000+ рядків коду видалено з core
- Досягнута повна незалежність модулів
