## 📋 Detailed Feature Breakdown

### 1️⃣ Multi-Tenancy (8-10 weeks)

**Epic**: Enable multiple organizations to use single Promenade instance with complete data isolation.

#### 1.1 Organization Context (Week 1-2)

**Tasks**:

- [ ] Create `shared/organization` bounded context
  - Organization aggregate (name, settings, status, limits)
  - Repository with PostgreSQL adapter
  - Use cases (Create, Update, Suspend, Delete)
  - HTTP handlers and DTOs
- [ ] Add `organization_id UUID` to all multi-tenant tables
  - Migration script for schema changes
  - Update all aggregates with OrganizationID field
  - Validate OrganizationID in all repositories
- [ ] Implement Organization middleware
  - Extract org ID from JWT token
  - Inject into request context
  - Validate user belongs to organization

**Acceptance Criteria**:

- ✅ Organization CRUD operations work
- ✅ All tables have organization_id column
- ✅ Middleware blocks cross-tenant access
- ✅ Integration tests with multiple orgs pass

**Technical Debt**:

- Decision: Row-level security (RLS) vs application-level filtering?
- Consider schema-per-tenant for larger deployments

---

#### 1.2 Tenant-Aware Queries (Week 3-4)

**Tasks**:

- [ ] Update ALL repository methods with org filtering
  - Customer context (5 repositories)
  - Identity context (5 repositories)
  - Order context (3 repositories)
  - Billing context (3 repositories)
  - Accounting context (7 repositories)
  - Banking context (3 repositories)
  - Warehouse context (4 repositories)
  - Fiscal context (2 repositories)
- [ ] Add organization_id to WHERE clauses
- [ ] Create helper function: `getExecutorWithOrg(ctx)`
- [ ] Update test fixtures with organization_id

**Example Pattern**:

```go
// Before
query := "SELECT * FROM customers WHERE id = $1"

// After
query := "SELECT * FROM customers WHERE id = $1 AND organization_id = $2"
orgID := middleware.GetOrganizationID(ctx)
```

**Acceptance Criteria**:

- ✅ All queries filter by organization_id
- ✅ Cross-tenant data access impossible
- ✅ All integration tests updated
- ✅ Performance impact <5% (benchmark tests)

#### 4.2 Automatic Reconciliation (Week 2)

**Tasks**:

- [ ] Implement matching algorithm
  - Match by amount + date range (±3 days)
  - Match by reference/description keywords
  - Fuzzy matching for customer names
  - Confidence scoring (0-100%)
- [ ] Create reconciliation UI
  - Unmatched transactions list
  - Suggested matches with confidence
  - Manual matching interface
  - Batch approval
- [ ] Reconciliation workflow
  - Auto-match high confidence (>90%)
  - Flag ambiguous matches for review
  - Create adjustment entries

**Matching Rules**:

1. Exact amount + exact date + description match = 100%
2. Exact amount + ±1 day = 95%
3. Exact amount + ±3 days + partial description = 80%
4. Amount ±5% + date range = 60%

**Acceptance Criteria**:

- ✅ >80% auto-match rate
- ✅ Zero false positives
- ✅ Manual override works
- ✅ Audit trail complete
