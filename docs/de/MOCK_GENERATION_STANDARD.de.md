# Standard für Mock-Generierung

Dieses Dokument definiert den einheitlichen Ansatz zur Mock-Generierung in allen Modulen des Promenade-Projekts.

## Philosophie

**Alle Mocks MÜSSEN mit mockery generiert werden**, um Folgendes sicherzustellen:

- Konsistenz über alle IModule hinweg
- Automatische Synchronisierung mit Interface-Änderungen
- Standardisierte Tooling- und CI/CD-Integration
- Reduzierter manueller Wartungsaufwand

## Konfiguration

Das Projekt verwendet eine zentralisierte Konfigurationsdatei `.mockery.yaml` auf der Root-Ebene, die die Mock-Generierung definiert für:

- Core repositories (`internal/domain/repository`)
- Alle Business-IModule (`internal/modules/*/domain/repository`)

## Installation

```bash
make install
# oder manuell:
go install github.com/vektra/mockery/v2@latest
```

## Verwendung

### Alle Mocks generieren

```bash
make mocks
```

Dieser Befehl:

1. Prüft, ob mockery installiert ist
2. Verwendet die `.mockery.yaml`-Konfiguration
3. Generiert Mocks für ALLE Repositories in ALLEN Modulen
4. Platziert Mocks an standardisierten Orten

### Modul-spezifische Mocks generieren

```bash
make mocks-audit      # Nur Audit-Modul
make mocks-posts      # Nur Posts-Modul
make mocks-profiles   # Nur Profiles-Modul
make mocks-analytics  # Nur Analytics-Modul
```

### Aktualität der Mocks überprüfen

```bash
make mocks-verify
```

Dies ist nützlich in CI/CD-Pipelines, um sicherzustellen, dass Entwickler nach Interface-Änderungen die Mocks nicht vergessen haben zu regenerieren.

## Standard für Mock-Platzierung

Jedes Modul folgt dieser Struktur:

```
internal/modules/{module_name}/
├── domain/
│   └── repository/
│       ├── {interface_name}.go           # Interface-Definition
│       └── mocks/
│           └── {interface_name}_mock.go  # Generierter Mock
```

Für Core-Repositories:

```
internal/
├── domain/
│   └── repository/
│       └── {interface_name}.go           # Interface-Definition
└── adapter/
    └── repository/
        └── mocks/
            └── {interface_name}_mock.go  # Generierter Mock
```

## Mock-Dateistruktur

Alle generierten Mocks haben diese Struktur:

```go
// Code generated by mockery v2.53.5. DO NOT EDIT.

package mocks

import (
    // imports...
)

// Mock{InterfaceName} is an autogenerated mock type
type Mock{InterfaceName} struct {
    mock.Mock
}

// Interface method implementations...
```

Bearbeiten Sie diese Dateien **NIEMALS** manuell. Alle Änderungen werden bei der nächsten Generierung überschrieben.

## Verwendung von Mocks in Tests

### Standard-Pattern

```go
package usecase

import (
    "testing"
    "github.com/stretchr/testify/mock"
    "github.com/basilex/promenade/internal/modules/audit/domain/repository/mocks"
)

func TestSomeUseCase(t *testing.T) {
    // Mock erstellen
    mockRepo := new(mocks.MockAuditEventRepository)

    // Erwartungen festlegen
    mockRepo.On("GetByID", mock.Anything, "test-id").Return(expectedEvent, nil)

    // Use Case mit Mock erstellen
    uc := NewAuditEventUseCase(mockRepo)

    // Testen
    result, err := uc.GetEvent(ctx, "test-id")

    // Assertions
    require.NoError(t, err)
    assert.Equal(t, expectedEvent, result)
    mockRepo.AssertExpectations(t)
}
```

## Modul-Unabhängigkeit

Die Mocks jedes Moduls sind **völlig unabhängig**:

- Mocks verwenden NUR Typen aus ihrem eigenen Modul
- Keine Imports aus `internal/domain` oder `internal/usecase`
- Nur `pkg/*`-Imports sind erlaubt
- Dies stellt sicher, dass IModule unabhängig aktiviert/deaktiviert werden können

## CI/CD-Integration

Fügen Sie Ihrer CI-Pipeline hinzu:

```yaml
- name: Verify mocks are up-to-date
  run: make mocks-verify
```

Dies stellt sicher, dass Entwickler Mocks regenerieren, wenn sich Interfaces ändern.

## Wann Mocks regeneriert werden sollten

Regenerieren Sie Mocks, wenn Sie:

1. Eine neue Methode zu einem Repository-Interface hinzufügen
2. Methodensignaturen ändern (Parameter oder Rückgabetypen)
3. Ein neues Repository-Interface hinzufügen
4. Ein Repository-Interface löschen

## Namenskonventionen

- **Interface**: `IAuditEventRepository`
- **Mock**: `MockAuditEventRepository`
- **Datei**: `audit_event_repository_mock.go`
- **Package**: `mocks`

Alle Namen werden automatisch von mockery aus dem Interface-Namen abgeleitet.

## Migration von manuellen Mocks

Wenn Sie manuelle Mocks haben (ohne "Code generated by mockery"-Header):

1. Sichern Sie Ihre Tests, wenn sie auf benutzerdefiniertem Mock-Verhalten basieren
2. Führen Sie `make mocks` zur Regenerierung aus
3. Aktualisieren Sie Tests, um Standard-mockery-Patterns zu verwenden
4. Entfernen Sie manuelle Mock-Implementierungen

## Fehlerbehebung

### Fehler: "mockery not found"

```bash
make install
```

### Fehler: "use of unsupported options detected"

Diese Warnung kann ignoriert werden. Sie erscheint bei Verwendung von Kommandozeilen-Flags, die `.mockery.yaml`-Einstellungen überschreiben.

### Tests schlagen nach Regenerierung fehl

Überprüfen Sie, dass Ihre Test-Erwartungen mit den tatsächlichen Interface-Signaturen übereinstimmen. Mockery ist strikt bei Typen.

### Mock fehlt erwartete Methode

Überprüfen Sie, dass das Interface die Methode hat, und regenerieren Sie:

```bash
make mocks-{module}
```

## Best Practices

1. **Niemals manuelle Mocks committen** - Verwenden Sie immer mockery-generierte Mocks
2. **Nach Interface-Änderungen regenerieren** - Vergessen Sie nicht, `make mocks` auszuführen
3. **`mock.Anything` für Kontexte verwenden** - Es sei denn, Sie testen kontextspezifisches Verhalten
4. **Erwartungen prüfen** - Rufen Sie am Ende der Tests immer `mockRepo.AssertExpectations(t)` auf
5. **Mocks einfach halten** - Komplexes Verhalten deutet darauf hin, dass das Interface möglicherweise zu breit ist

## Zusammenfassung

 **TUN**:

- mockery für ALLE Mock-Generierung verwenden
- `make mocks` nach Interface-Änderungen ausführen
- Standard-Mock-Patterns in Tests verwenden
- IModule unabhängig halten

 **NICHT TUN**:

- Generierte Mock-Dateien nicht manuell bearbeiten
- Keine manuellen Mock-Implementierungen erstellen
- Keine Core-Packages in Modul-Mocks importieren
- Keine veralteten Mocks committen, die nicht mit Interfaces übereinstimmen

---

**Compliance**: Dieser Standard ist für alle IModule obligatorisch. Alle vorhandenen manuellen Mocks sollten zu mockery-generierten Mocks migriert werden.
