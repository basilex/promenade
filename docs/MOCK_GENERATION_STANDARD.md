# Mock Generation Standard

This document defines the unified approach to mock generation across all modules in the Promenade project.

## Philosophy

**All mocks MUST be generated using mockery** to ensure:

- Consistency across all modules
- Automatic synchronization with interface changes
- Standard tooling and CI/CD integration
- Reduced manual maintenance burden

## Configuration

The project uses a centralized `.mockery.yaml` configuration file at the root level that defines mock generation for:

- Core repositories (`internal/domain/repository`)
- All business modules (`internal/modules/*/domain/repository`)

## Installation

```bash
make install
# or manually:
go install github.com/vektra/mockery/v2@latest
```

## Usage

### Generate All Mocks

```bash
make mocks
```

This command:

1. Checks if mockery is installed
2. Uses `.mockery.yaml` configuration
3. Generates mocks for ALL repositories in ALL modules
4. Places mocks in standardized locations

### Generate Module-Specific Mocks

```bash
make mocks-audit      # Audit module only
make mocks-posts      # Posts module only
make mocks-profiles   # Profiles module only
make mocks-analytics  # Analytics module only
```

### Verify Mocks Are Up-to-Date

```bash
make mocks-verify
```

This is useful in CI/CD pipelines to ensure developers haven't forgotten to regenerate mocks after interface changes.

## Mock Location Standard

Each module follows this structure:

```
internal/modules/{module_name}/
├── domain/
│   └── repository/
│       ├── {interface_name}.go           # Interface definition
│       └── mocks/
│           └── {interface_name}_mock.go  # Generated mock
```

For core repositories:

```
internal/
├── domain/
│   └── repository/
│       └── {interface_name}.go           # Interface definition
└── adapter/
    └── repository/
        └── mocks/
            └── {interface_name}_mock.go  # Generated mock
```

## Mock File Structure

All generated mocks have this structure:

```go
// Code generated by mockery v2.53.5. DO NOT EDIT.

package mocks

import (
    // imports...
)

// Mock{InterfaceName} is an autogenerated mock type
type Mock{InterfaceName} struct {
    mock.Mock
}

// Interface method implementations...
```

**NEVER** edit these files manually. Any changes will be overwritten on next generation.

## Using Mocks in Tests

### Standard Pattern

```go
package usecase

import (
    "testing"
    "github.com/stretchr/testify/mock"
    "github.com/basilex/promenade/internal/modules/audit/domain/repository/mocks"
)

func TestSomeUseCase(t *testing.T) {
    // Create mock
    mockRepo := new(mocks.MockAuditEventRepository)

    // Set expectations
    mockRepo.On("GetByID", mock.Anything, "test-id").Return(expectedEvent, nil)

    // Create use case with mock
    uc := NewAuditEventUseCase(mockRepo)

    // Test
    result, err := uc.GetEvent(ctx, "test-id")

    // Assertions
    require.NoError(t, err)
    assert.Equal(t, expectedEvent, result)
    mockRepo.AssertExpectations(t)
}
```

## Module Independence

Each module's mocks are **completely independent**:

- Mocks use ONLY types from their own module
- No imports from `internal/domain` or `internal/usecase`
- Only `pkg/*` imports are allowed
- This ensures modules can be enabled/disabled independently

## CI/CD Integration

Add to your CI pipeline:

```yaml
- name: Verify mocks are up-to-date
  run: make mocks-verify
```

This ensures developers regenerate mocks when interfaces change.

## When to Regenerate Mocks

Regenerate mocks whenever you:

1. Add a new method to a repository interface
2. Change method signatures (parameters or return types)
3. Add a new repository interface
4. Delete a repository interface

## Naming Conventions

- **Interface**: `AuditEventRepository`
- **Mock**: `MockAuditEventRepository`
- **File**: `audit_event_repository_mock.go`
- **Package**: `mocks`

All names are automatically derived by mockery from the interface name.

## Migration from Manual Mocks

If you have manual mocks (without "Code generated by mockery" header):

1. Backup your tests if they rely on custom mock behavior
2. Run `make mocks` to regenerate
3. Update tests to use standard mockery patterns
4. Remove manual mock implementations

## Troubleshooting

### Error: "mockery not found"

```bash
make install
```

### Error: "use of unsupported options detected"

This warning can be ignored. It appears when using command-line flags that override `.mockery.yaml` settings.

### Tests fail after regeneration

Check that your test expectations match the actual interface signatures. Mockery is strict about types.

### Mock missing expected method

Verify the interface has the method and regenerate:

```bash
make mocks-{module}
```

## Best Practices

1. **Never commit manual mocks** - Always use mockery-generated mocks
2. **Regenerate after interface changes** - Don't forget to run `make mocks`
3. **Use `mock.Anything` for contexts** - Unless testing context-specific behavior
4. **Assert expectations** - Always call `mockRepo.AssertExpectations(t)` at end of tests
5. **Keep mocks simple** - Complex behavior indicates the interface might be too broad

## Summary

✅ **DO**:

- Use mockery for ALL mock generation
- Run `make mocks` after interface changes
- Use standard mock patterns in tests
- Keep modules independent

❌ **DON'T**:

- Edit generated mock files manually
- Create manual mock implementations
- Import core packages in module mocks
- Commit stale mocks that don't match interfaces

---

**Compliance**: This standard is mandatory for all modules. All existing manual mocks should be migrated to mockery-generated mocks.
